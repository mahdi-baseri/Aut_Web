## سؤال ۱: تفاوت merge و rebase

هر دو دستور برای ترکیب تغییرات شاخه‌ها استفاده می‌شوند، ولی روش کارشان یکی نیست.

**git merge:** تغییرات دو شاخه را با هم ادغام می‌کند و تاریخچه قبلی کامیت‌ها را نگه می‌دارد. وقتی هر دو شاخه کامیت جدید داشته باشند، معمولاً یک کامیت جدید برای ادغام ساخته می‌شود. البته اگر شاخه اصلی جلو نرفته باشد، ممکن است ادغام به صورت `fast-forward` انجام شود و کامیت جداگانه‌ای ساخته نشود.

مثلاً وقتی یک قابلیت را در شاخه جداگانه کامل کرده‌ام و می‌خواهم آن را وارد `main` کنم:

```bash
git switch main
git merge feature-description
```

در کار گروهی معمولاً `merge` را ترجیح می‌دهم، چون کامیت‌های قبلی را تغییر نمی‌دهد و معلوم می‌ماند شاخه‌ها چطور با هم ادغام شده‌اند.

**git rebase:** کامیت‌های شاخه فعلی را دوباره روی آخرین کامیت‌های شاخه مبنا اعمال می‌کند. به این شکل تاریخچه معمولاً خطی‌تر می‌شود. چون کامیت‌ها دوباره ساخته می‌شوند، شناسه آن‌ها هم عوض می‌شود.

مثلاً وقتی در شاخه شخصی‌ام کار می‌کنم و می‌خواهم تغییرات جدید `main` را وارد آن کنم:

```bash
git switch feature-description
git rebase main
```

اینجا `rebase` مناسب است، چون تاریخچه شاخه شخصی‌ام مرتب‌تر می‌ماند. اما برای شاخه‌ای که بقیه هم از کامیت‌هایش استفاده می‌کنند، معمولاً `rebase` نمی‌زنم؛ چون تغییر تاریخچه ممکن است کار بقیه را به مشکل بزند.

در کل، `merge` تاریخچه شاخه‌ها را حفظ می‌کند، ولی `rebase` با ساختن دوباره کامیت‌ها معمولاً تاریخچه خطی‌تری می‌دهد.

## سؤال ۲: انتخاب بخشی از تغییرات برای کامیت

در خروجی `git diff`، به یک قسمت از خطوط تغییرکرده که همراه چند خط اطرافش نمایش داده می‌شود، `hunk` می‌گویند. یک فایل می‌تواند چند hunk داشته باشد. مثلاً ممکن است هم ابتدای فایل را تغییر داده باشم و هم چند خط از انتهای آن را.

برای دیدن تغییرات فایل `README.md` و انتخاب فقط بعضی از آن‌ها از این دستورها استفاده می‌کنم:

```bash
git diff -- README.md
git add -p -- README.md
```

دستور دوم بخش‌های تغییرکرده را یکی‌یکی نشان می‌دهد و می‌پرسد کدامشان وارد `staging` شوند:

- `y`: این بخش اضافه شود.
- `n`: این بخش فعلاً اضافه نشود.
- `s`: اگر امکان داشته باشد، بخش را به چند قسمت کوچک‌تر تقسیم کند.
- `e`: اجازه بدهد انتخاب خطوط را با ویرایش دستی patch انجام بدهم.
- `q`: از انتخاب تعاملی خارج شود.

بعد از انتخاب قسمت‌های موردنظر، بررسی می‌کنم چه تغییراتی آماده کامیت هستند و سپس آن‌ها را ثبت می‌کنم:

```bash
git diff --cached -- README.md
git status
git commit -m "Update README introduction"
```

فایده این روش این است که تغییرات نامرتبط را در یک کامیت قاطی نمی‌کنم. مثلاً اگر هم یک متن را اصلاح کرده باشم و هم قسمت دیگری از فایل را تغییر داده باشم، می‌توانم این دو کار را جدا ثبت کنم. بخش‌هایی که انتخاب نکرده‌ام در فایل محلی باقی می‌مانند و وارد آن کامیت نمی‌شوند.

## سؤال ۳: پیدا کردن کامیتی که خطا را ایجاد کرده

وقتی می‌دانم پروژه قبلاً درست کار می‌کرده ولی الان مشکلی دارد، با `git bisect` می‌توانم کامیتی را پیدا کنم که مشکل از آن شروع شده است. این دستور به‌جای بررسی تک‌تک کامیت‌ها، هر بار تقریباً وسط بازه را انتخاب می‌کند تا تعداد بررسی‌ها کمتر شود.

فرض می‌کنم دکمه ثبت‌نام سایت در نسخه فعلی خراب است، اما در کامیت فرضی `a1b2c3d` درست کار می‌کرده. اول جست‌وجو را شروع می‌کنم:

```bash
git bisect start
git bisect bad HEAD
git bisect good a1b2c3d
```

بعد Git یکی از کامیت‌های بین نسخه سالم و خراب را انتخاب می‌کند. پروژه را در آن نسخه امتحان می‌کنم:

- اگر مشکل وجود نداشت، می‌زنم `git bisect good`.
- اگر مشکل وجود داشت، می‌زنم `git bisect bad`.

این کار را تکرار می‌کنم تا Git اولین کامیتی را که باعث خطا شده مشخص کند. در آخر هم از حالت جست‌وجو خارج می‌شوم:

```bash
git bisect reset
```

به نظرم این روش مخصوصاً وقتی تعداد کامیت‌ها زیاد باشد خیلی کاربردی است، چون لازم نیست همه نسخه‌ها را یکی‌یکی بررسی کنم.

## سؤال ۴: بررسی تغییرات قبل از کامیت

در صورت سؤال، فایل `README.md` از قبل تحت پیگیری Git بوده است. یک سری تغییر را وارد `staging` کرده‌ام و بعد دوباره فایل را تغییر داده‌ام، اما تغییرات جدید را هنوز به `staging` نفرستاده‌ام.

**۱. بررسی وضعیت و تغییرات**

```bash
git status
git diff -- README.md
git diff --cached -- README.md
```

- `git status` وضعیت فایل‌ها و تغییرات `staged` و `unstaged` را نشان می‌دهد.
- `git diff -- README.md` تغییرات فایل محلی نسبت به نسخه داخل `staging` را نشان می‌دهد؛ یعنی تغییرات جدیدی که هنوز آماده کامیت نشده‌اند.
- `git diff --cached -- README.md` تغییرات داخل `staging` نسبت به آخرین کامیت را نشان می‌دهد؛ یعنی همان قسمت‌هایی که آماده ثبت هستند.

اگر بخواهم همه تغییرات فایل نسبت به آخرین کامیت را یک‌جا ببینم، از این دستور استفاده می‌کنم:

```bash
git diff HEAD -- README.md
```

**۲. اگر همین الان یک کامیت معمولی ثبت کنم**

```bash
git commit -m "Update README"
```

فقط تغییراتی که قبلاً وارد `staging` کرده‌ام ثبت می‌شوند. ویرایش‌هایی که بعداً انجام داده‌ام و هنوز `stage` نشده‌اند، در `working tree` باقی می‌مانند. دلیلش هم این است که `git commit` معمولی، بدون گزینه `-a`، خودش تغییرات جدید فایل را به `staging` اضافه نمی‌کند.

**۳. جلوگیری از ثبت فایل‌های موقت**

در فایل `.gitignore` که در ریشه مخزن قرار دارد، این خط را می‌نویسم:

```gitignore
tmp/
```

با این کار، Git فایل‌های `untracked` داخل پوشه `tmp/` را نادیده می‌گیرد. اما اگر یک فایل قبلاً `tracked` شده باشد، اضافه کردن آن به `.gitignore` کافی نیست. باید آن را از فهرست فایل‌های تحت پیگیری خارج کنم، بدون اینکه از کامپیوترم پاک شود:

```bash
git rm --cached -- path/to/tracked-file
```

اگر چند فایل tracked داخل پوشه `tmp/` وجود داشته باشد، می‌توانم از دستور زیر استفاده کنم:

```bash
git rm -r --cached -- tmp/
```

بعد هم باید این تغییر را کامیت کنم. فایل‌های اصلی روی سیستمم باقی می‌مانند.

## سؤال ۵: رفع merge conflict در کار گروهی

**۱. علت به وجود آمدن conflict**

من در شاخه `feature-description` و هم‌تیمی‌ام در `main` یک خط مشترک از `README.md` را به دو شکل متفاوت عوض کرده‌ایم. موقع ادغام، Git نمی‌تواند خودش تشخیص بدهد کدام متن باید باقی بماند؛ برای همین `conflict` ایجاد می‌شود.

البته هر تغییری که دو نفر در یک فایل بدهند لزوماً باعث conflict نمی‌شود. اگر قسمت‌های جداگانه‌ای از فایل را تغییر داده باشند، Git معمولاً خودش آن‌ها را ادغام می‌کند.

**۲. پیدا کردن فایل و قسمت‌های دارای conflict**

```bash
git switch main
git merge feature-description
git status
git diff --name-only --diff-filter=U
```

`git status` فایل‌های دارای مشکل را نشان می‌دهد و دستور آخر اسم فایل‌هایی را می‌دهد که تداخلشان هنوز حل نشده است. داخل فایل ممکن است چیزی شبیه این ببینم:

```text
<<<<<<< HEAD
متن شاخه main
=======
متن شاخه feature-description
>>>>>>> feature-description
```

علامت `<<<<<<<` شروع متن یک طرف است (اینجا `HEAD` یعنی `main`). علامت `=======` دو نسخه را جدا می‌کند و `>>>>>>>` انتهای متن طرف دوم را نشان می‌دهد. این علامت‌ها فقط برای مشخص شدن محل اختلاف هستند و نباید در متن نهایی باقی بمانند.

**۳. حل کردن conflict و کامل کردن merge**

چون در سؤال گفته شده اطلاعات هر دو نفر باید حفظ شود، فایل را باز می‌کنم و یک متن جدید می‌نویسم که هر دو تغییر در آن باشد. مثلاً:

> برای این پروژه هم راهنمای نصب نوشته شده و هم امکانات جدید آن توضیح داده شده است.

بعد علامت‌های conflict را از فایل حذف می‌کنم و متن را دوباره می‌خوانم تا مطمئن شوم چیزی جا نمانده است. سپس این دستورها را اجرا می‌کنم:

```bash
git add README.md
git diff --cached --check
git status
git merge --continue
git status
```

`git add` به Git اعلام می‌کند که تداخل این فایل را حل کرده‌ام. دستور `git diff --cached --check` هم می‌تواند بعضی خطاها، از جمله علامت‌های conflict باقی‌مانده در تغییرات آماده ثبت، را پیدا کند. با این حال خود فایل را هم بررسی می‌کنم. در نهایت `git merge --continue` ادغام را کامل می‌کند و با `git status` وضعیت نهایی را می‌بینم.

**۴. اگر بخواهم ادغام را لغو کنم**

```bash
git merge --abort
```

این دستور merge در حال انجام را لغو می‌کند. چون طبق صورت سؤال قبل از شروع ادغام تغییر ثبت‌نشده‌ای نداشته‌ایم، وضعیت به قبل از merge برمی‌گردد.

## سؤال ۶: انتخاب روش مناسب برای برگرداندن تغییرات

**حالت اول: تغییرات notes.txt هنوز وارد staging نشده‌اند و دیگر آن‌ها را نمی‌خواهم.**

```bash
git restore --worktree -- notes.txt
```

این دستور تغییرات فایل را در `working tree` کنار می‌گذارد و نسخه داخل `staging` را برمی‌گرداند. در این سؤال، نسخه staging همان نسخه آخرین کامیت است. بقیه فایل‌ها، staging و تاریخچه کامیت‌ها تغییر نمی‌کنند. باید حواسم باشد که با این دستور ممکن است ویرایش‌های کنارگذاشته‌شده را از دست بدهم.

**حالت دوم: فایل را اشتباهی وارد staging کرده‌ام، ولی می‌خواهم ویرایش‌هایم بمانند.**

```bash
git restore --staged -- notes.txt
```

این دستور تغییرات فایل را از `staging` خارج می‌کند، ولی متن ویرایش‌شده در `working tree` باقی می‌ماند. تاریخچه کامیت‌ها هم عوض نمی‌شود.

**حالت سوم: یک کامیت اشتباه را روی main پوش کرده‌ام و بقیه هم آن را دریافت کرده‌اند.**

```bash
git switch main
git revert <commit-hash>
git push origin main
```

در این دستور، به‌جای `<commit-hash>` شناسه کامیت اشتباه را می‌گذارم. `git revert` یک کامیت جدید می‌سازد که اثر کامیت اشتباه را برعکس می‌کند، بدون اینکه خود آن کامیت را از تاریخچه پاک کند. بعد با `git push` نتیجه را برای بقیه می‌فرستم. با فرض سؤال که conflict نداریم، بعد از تکمیل کار معمولاً `working tree` دوباره تمیز می‌شود.

اینجا `reset` همراه با `force push` انتخاب خوبی نیست، چون تاریخچه شاخه مشترک را بازنویسی می‌کند و ممکن است کار هم‌تیمی‌هایی را که آن کامیت را دریافت کرده‌اند به مشکل بیندازد. برای همین `revert` راه مناسب‌تری است.

## تمرین دوم - HTTP

### سؤال ۱: تفاوت نسخه‌های HTTP

تفاوت نسخه‌های HTTP را به صورت خلاصه می‌توان این‌طور گفت:

- **HTTP/0.9:** نسخه خیلی ساده و اولیه، فقط درخواست `GET`، بدون هدر و کد وضعیت، بیشتر برای دریافت متن HTML.
- **HTTP/1.0:** اضافه شدن هدرها، کدهای وضعیت و روش‌هایی مثل `POST` و `HEAD`. اتصال معمولاً برای هر درخواست جداگانه برقرار و بسته می‌شد.
- **HTTP/1.1:** اتصال‌های ماندگار (`keep-alive`)، اجباری شدن هدر `Host`، پشتیبانی از `chunked transfer` و بهتر شدن مدیریت کش. یعنی می‌شد چند درخواست را از یک اتصال استفاده کرد.
- **HTTP/2:** ارسال داده‌ها به شکل باینری، انجام هم‌زمان چند درخواست روی یک اتصال (`multiplexing`) و فشرده‌سازی هدرها با `HPACK`. البته هنوز از `TCP` استفاده می‌کرد.
- **HTTP/3:** استفاده از `QUIC` به جای TCP، انتقال روی `UDP`، راه‌اندازی سریع‌تر اتصال، امنیت با `TLS 1.3` و جریان‌های مستقل‌تر. فشرده‌سازی هدرها هم با `QPACK` انجام می‌شود.

**چرا HTTP/3 از UDP استفاده می‌کند؟**

در HTTP/2 چند درخواست می‌توانند هم‌زمان روی یک اتصال TCP باشند، ولی اگر یک بسته TCP گم شود، دریافت داده‌های بقیه درخواست‌ها هم ممکن است منتظر بماند. به این مشکل `Head-of-Line Blocking` در سطح TCP می‌گویند. در HTTP/3 از `QUIC` استفاده می‌شود که روی UDP کار می‌کند و برای هر جریان، مدیریت مستقل‌تری دارد. پس گم شدن بسته یک جریان لزوماً بقیه جریان‌ها را متوقف نمی‌کند. QUIC خودش قابلیت‌هایی مثل ارسال قابل‌اعتماد، کنترل ازدحام و رمزنگاری را دارد؛ بنابراین استفاده از UDP به این معنی نیست که داده‌ها بدون کنترل و اطمینان ارسال می‌شوند. دلیل اصلی این انتخاب، انعطاف و کاهش تأخیر ارتباط است.

### سؤال ۲: تفاوت Stateful و Stateless

**الف)** در ارتباط `stateless` هر درخواست مستقل از درخواست‌های قبلی بررسی می‌شود و سرور لازم نیست اطلاعات درخواست قبل را به خاطر داشته باشد. ولی در ارتباط `stateful` وضعیت قبلی کاربر یا ارتباط نگهداری می‌شود و درخواست بعدی می‌تواند به آن وابسته باشد. مثلاً در یک فروشگاه اینترنتی، اگر سایت بداند قبلاً چه محصولی در سبد خرید گذاشته‌ام، از اطلاعات قبلی من استفاده کرده است.

**ب)** خود پروتکل `HTTP` از نوع `stateless` است. یعنی سرور فقط از روی یک درخواست HTTP، لزوماً نمی‌فهمد همان کاربر قبلاً چه کاری انجام داده است. برای حل این موضوع معمولاً از `Cookie` و `Session` استفاده می‌کنند. مثلاً بعد از ورود به سایت، یک شناسه نشست داخل کوکی مرورگر قرار می‌گیرد و در درخواست‌های بعدی فرستاده می‌شود تا سرور بتواند کاربر را بشناسد. در بعضی سیستم‌ها هم از توکن‌هایی مثل `JWT` برای فرستادن اطلاعات احراز هویت استفاده می‌شود. این روش‌ها وضعیت کاربر را در سطح برنامه مدیریت می‌کنند، نه اینکه ذات HTTP را stateful کنند.

### سؤال ۳: محدودیت HTTP برای ارتباط لحظه‌ای و راه‌حل‌های آن

**الف) مشکل چیست؟**

در مدل معمول HTTP، اول کلاینت باید درخواست بفرستد و بعد سرور پاسخ می‌دهد. برای کارهایی مثل چت یا اعلام هشدار، ممکن است سرور هر لحظه پیام جدیدی داشته باشد، ولی نمی‌تواند بدون یک سازوکار اضافه، یک پاسخ HTTP معمولی را خودبه‌خود برای مرورگری که درخواستی نفرستاده ارسال کند. برای همین باید روشی داشته باشیم که کلاینت مرتب پیگیری کند یا یک مسیر ارتباطی برای دریافت پیام باز نگه دارد.

**ب) راه‌حل‌ها:**

**Polling معمولی:** مرورگر هر چند ثانیه یک بار از سرور می‌پرسد آیا پیام جدیدی آمده یا نه. پیاده‌سازی آن ساده است، اما اگر خبری نباشد هم درخواست‌های زیادی فرستاده می‌شود و ممکن است پیام با چند ثانیه تأخیر برسد. برای اطلاعاتی که زیاد تغییر نمی‌کنند روش بدی نیست.

**Long Polling:** کلاینت درخواست می‌فرستد، ولی سرور تا وقتی پیام تازه‌ای نداشته باشد پاسخ را نگه می‌دارد. بعد از رسیدن پیام، پاسخ را می‌فرستد و کلاینت دوباره درخواست جدیدی ایجاد می‌کند. این روش نسبت به Polling معمولی تأخیر کمتری دارد، هرچند مدیریت تعداد زیاد درخواست‌های باز می‌تواند برای سرور هزینه داشته باشد.

**Server-Sent Events یا SSE:** مرورگر با `EventSource` یک درخواست به سرور می‌فرستد و سرور همان ارتباط را برای ارسال رویدادهای جدید باز نگه می‌دارد. ارتباط در این روش یک‌طرفه، یعنی از سرور به کلاینت است. برای اعلان‌ها، نمایش وضعیت لحظه‌ای و خبرهای جدید مناسب است، اما برای فرستادن پیام از کلاینت به سرور باید جداگانه درخواست فرستاد.

**WebSocket:** در شروع، کلاینت ارتباط را برقرار می‌کند و بعد یک ارتباط دوطرفه و ماندگار شکل می‌گیرد. از آن به بعد سرور و کلاینت می‌توانند بدون ساختن یک درخواست HTTP جدید برای هر پیام، برای هم داده بفرستند. برای چت آنلاین و بازی‌های چندنفره انتخاب مناسبی است، چون تأخیر کمی دارد و ارتباط دوطرفه است.

**Webhook:** بیشتر برای ارتباط بین دو سرویس استفاده می‌شود. سرویس دریافت‌کننده یک آدرس مشخص (endpoint) در اختیار سرویس دیگر می‌گذارد؛ وقتی رویدادی مثل ثبت سفارش اتفاق بیفتد، سرویس اول به آن آدرس یک درخواست HTTP، معمولاً `POST`، می‌فرستد. در واقع سرویس فرستنده در آن لحظه نقش کلاینت را دارد. پس Webhook محدودیت HTTP را نقض نمی‌کند، بلکه با یک درخواست جدید، اطلاع‌رسانی را انجام می‌دهد.

**Web Push:** برای اعلان‌های مرورگر می‌توان از Push API و Service Worker استفاده کرد. کاربر ابتدا باید اجازه بدهد و در سرویس اعلان عضو شود؛ بعد سیستم می‌تواند حتی وقتی صفحه سایت باز نیست، اعلان را به مرورگر برساند. این روش برای نوتیفیکیشن مناسب‌تر است و جای ارتباط دائمی چت را نمی‌گیرد.

### سؤال ۴: اجزای URL داده‌شده

آدرس سؤال به این شکل است:

`ss://asghar:1234!!@ss.myproxy.com:1234#shadowSocks1`

- **Scheme:** مقدار `ss` است. این پیشوند معمولاً برای آدرس‌های `Shadowsocks` به کار می‌رود و به معنی HTTP یا HTTPS نیست.
- **User info:** بخش `asghar:1234!!` قبل از `@` قرار دارد. در ساختار عمومی URL، این قسمت شبیه `username:password` است؛ اما در قالب Shadowsocks معمولاً قسمت اول، روش رمزنگاری (`method`) و قسمت دوم، رمز عبور (`password`) است. پس در این مثال `asghar` قسمت اول و `1234!!` رمز عبور است.
- **Host:** مقدار `ss.myproxy.com` است؛ یعنی نام سروری که باید به آن متصل شویم.
- **Port:** عدد `1234` بعد از نام هاست است.
- **Fragment / Tag:** قسمت بعد از `#` یعنی `shadowSocks1` است که می‌تواند برچسب یا اسم این اتصال باشد.
- **Path و Query:** در این آدرس مشخص نشده‌اند؛ چون نه مسیر جداگانه‌ای بعد از هاست داریم و نه علامت `?` برای پارامترهای Query آمده است.

یک نکته هم این است که `asghar` اسم یک الگوریتم رمزنگاری شناخته‌شده در Shadowsocks نیست؛ بنابراین این URL را به‌عنوان مثالِ تجزیه اجزای آدرس در نظر می‌گیرم، نه لزوماً یک تنظیم قابل‌استفاده.

### سؤال ۵: انتخاب HTTP Status Code

**۱. دیتابیس مشکل پیدا کرده و ورود به سایت انجام نمی‌شود.**

کد پیشنهادی من `503 Service Unavailable` است، مخصوصاً اگر اختلال موقت باشد و سرویس فعلاً نتواند درخواست‌های ورود را پاسخ دهد. اگر یک خطای داخلی پیش‌بینی‌نشده باشد، `500 Internal Server Error` هم ممکن است برگردد. چون مشکل از سمت سرور است، نباید کد خطای مربوط به کاربر بدهیم.

**۲. نام کاربری واردشده وجود ندارد و ورود ناموفق است.**

کد `401 Unauthorized` را انتخاب می‌کنم، چون اطلاعات احراز هویت معتبر نبوده و کاربر وارد نشده است. بهتر است در پیام عمومی ورود مشخص نکنیم نام کاربری وجود دارد یا نه تا کسی نتواند نام کاربران واقعی را راحت حدس بزند. برای همین `404` را برای یک درخواست معمولی لاگین انتخاب نمی‌کنم.

**۳. سایت به دامنه دیگری منتقل شده است.**

اگر انتقال دائمی باشد، `301 Moved Permanently` مناسب است. `308 Permanent Redirect` هم گزینه خوبی است، مخصوصاً وقتی بخواهیم نوع درخواست و بدنه آن در تغییر مسیر حفظ شوند. آدرس جدید هم در هدر `Location` برمی‌گردد. اگر انتقال موقت باشد، به جای این‌ها می‌توان از `302` یا `307` استفاده کرد.

**۴. تعداد درخواست‌های کاربر بیشتر از حد مجاز شده است.**

کد `429 Too Many Requests` مناسب است. چون سرور برای جلوگیری از فشار زیاد یا سوءاستفاده، تعداد درخواست‌ها را محدود کرده است. می‌توان هدر `Retry-After` را هم فرستاد تا کاربر بداند چه زمانی دوباره تلاش کند.

**۵. تمدید JWT موفق بوده و توکن جدید داخل هدر برگشته است.**

کد `200 OK` مناسب است، چون عملیات موفق شده است. اگر پاسخ هیچ محتوایی در بدنه نداشته باشد و فقط هدر حاوی توکن باشد، `204 No Content` هم قابل استفاده است. مهم این است که انتخاب کد با شکل پاسخ API هماهنگ باشد.

**۶. آی‌پی کاربر در محدوده ممنوعه قرار دارد.**

کد `403 Forbidden` را انتخاب می‌کنم، چون سرور درخواست را متوجه شده ولی طبق سیاست دسترسی، به این آی‌پی اجازه استفاده از سرویس نمی‌دهد. اگر محدودیت مشخصاً به دلیل یک الزام قانونی باشد، `451 Unavailable For Legal Reasons` هم می‌تواند مناسب باشد؛ اما برای مسدودسازی عادی بر اساس آی‌پی، `403` انتخاب معمول‌تری است.

### سؤال ۶: تشخیص نوع Proxy

**۱. دریافت پکیج‌ها از سرور داخلی دانشگاه به‌جای سرور اصلی:**

اگر سرور دانشگاه درخواست کاربران را دریافت کند و بسته‌ها را از منبع اصلی بگیرد و برای دفعات بعد ذخیره کند، این یک `Caching Forward Proxy` است. این کار باعث کاهش مصرف اینترنت و سریع‌تر شدن دانلودها می‌شود. البته اگر دانشگاه خودش یک کپی مستقل از مخزن پکیج‌ها داشته باشد، اسم دقیق‌تر آن `Repository Mirror` است، نه لزوماً پروکسی.

**۲. تقسیم درخواست‌ها بر اساس موقعیت جغرافیایی:**

می‌توان از `Reverse Proxy` همراه با `Geo-based Load Balancing` استفاده کرد. این سیستم بر اساس موقعیت تقریبی آی‌پی کاربر، درخواست را به سرور نزدیک‌تر یا مناسب‌تر می‌فرستد. این کار در CDNها هم دیده می‌شود و می‌تواند تأخیر را کمتر کند. البته مسیر‌دهی جغرافیایی گاهی با GeoDNS هم انجام می‌شود که خودش یک پروکسی نیست.

**۳. اضافه کردن احراز هویت به یک سرویس خیلی قدیمی:**

یک `Reverse Proxy` یا `API Gateway` جلوی سرویس قدیمی می‌گذاریم. درخواست‌ها اول به آن می‌رسند و بعد از بررسی لاگین یا توکن، فقط درخواست‌های مجاز به سرویس اصلی فرستاده می‌شوند. به این شکل بدون دست بردن زیاد در کد برنامه قدیمی، می‌توان یک لایه احراز هویت به آن اضافه کرد.
