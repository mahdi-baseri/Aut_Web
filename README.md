## سؤال ۱: تفاوت merge و rebase

هر دو دستور برای ترکیب تغییرات شاخه‌ها استفاده می‌شوند، ولی روش کارشان یکی نیست.

**git merge:** تغییرات دو شاخه را با هم ادغام می‌کند و تاریخچه قبلی کامیت‌ها را نگه می‌دارد. وقتی هر دو شاخه کامیت جدید داشته باشند، معمولاً یک کامیت جدید برای ادغام ساخته می‌شود. البته اگر شاخه اصلی جلو نرفته باشد، ممکن است ادغام به صورت `fast-forward` انجام شود و کامیت جداگانه‌ای ساخته نشود.

مثلاً وقتی یک قابلیت را در شاخه جداگانه کامل کرده‌ام و می‌خواهم آن را وارد `main` کنم:

```bash
git switch main
git merge feature-description
```

در کار گروهی معمولاً `merge` را ترجیح می‌دهم، چون کامیت‌های قبلی را تغییر نمی‌دهد و معلوم می‌ماند شاخه‌ها چطور با هم ادغام شده‌اند.

**git rebase:** کامیت‌های شاخه فعلی را دوباره روی آخرین کامیت‌های شاخه مبنا اعمال می‌کند. به این شکل تاریخچه معمولاً خطی‌تر می‌شود. چون کامیت‌ها دوباره ساخته می‌شوند، شناسه آن‌ها هم عوض می‌شود.

مثلاً وقتی در شاخه شخصی‌ام کار می‌کنم و می‌خواهم تغییرات جدید `main` را وارد آن کنم:

```bash
git switch feature-description
git rebase main
```

اینجا `rebase` مناسب است، چون تاریخچه شاخه شخصی‌ام مرتب‌تر می‌ماند. اما برای شاخه‌ای که بقیه هم از کامیت‌هایش استفاده می‌کنند، معمولاً `rebase` نمی‌زنم؛ چون تغییر تاریخچه ممکن است کار بقیه را به مشکل بزند.

در کل، `merge` تاریخچه شاخه‌ها را حفظ می‌کند، ولی `rebase` با ساختن دوباره کامیت‌ها معمولاً تاریخچه خطی‌تری می‌دهد.

## سؤال ۲: انتخاب بخشی از تغییرات برای کامیت

در خروجی `git diff`، به یک قسمت از خطوط تغییرکرده که همراه چند خط اطرافش نمایش داده می‌شود، `hunk` می‌گویند. یک فایل می‌تواند چند hunk داشته باشد. مثلاً ممکن است هم ابتدای فایل را تغییر داده باشم و هم چند خط از انتهای آن را.

برای دیدن تغییرات فایل `README.md` و انتخاب فقط بعضی از آن‌ها از این دستورها استفاده می‌کنم:

```bash
git diff -- README.md
git add -p -- README.md
```

دستور دوم بخش‌های تغییرکرده را یکی‌یکی نشان می‌دهد و می‌پرسد کدامشان وارد `staging` شوند:

- `y`: این بخش اضافه شود.
- `n`: این بخش فعلاً اضافه نشود.
- `s`: اگر امکان داشته باشد، بخش را به چند قسمت کوچک‌تر تقسیم کند.
- `e`: اجازه بدهد انتخاب خطوط را با ویرایش دستی patch انجام بدهم.
- `q`: از انتخاب تعاملی خارج شود.

بعد از انتخاب قسمت‌های موردنظر، بررسی می‌کنم چه تغییراتی آماده کامیت هستند و سپس آن‌ها را ثبت می‌کنم:

```bash
git diff --cached -- README.md
git status
git commit -m "Update README introduction"
```

فایده این روش این است که تغییرات نامرتبط را در یک کامیت قاطی نمی‌کنم. مثلاً اگر هم یک متن را اصلاح کرده باشم و هم قسمت دیگری از فایل را تغییر داده باشم، می‌توانم این دو کار را جدا ثبت کنم. بخش‌هایی که انتخاب نکرده‌ام در فایل محلی باقی می‌مانند و وارد آن کامیت نمی‌شوند.

## سؤال ۳: پیدا کردن کامیتی که خطا را ایجاد کرده

وقتی می‌دانم پروژه قبلاً درست کار می‌کرده ولی الان مشکلی دارد، با `git bisect` می‌توانم کامیتی را پیدا کنم که مشکل از آن شروع شده است. این دستور به‌جای بررسی تک‌تک کامیت‌ها، هر بار تقریباً وسط بازه را انتخاب می‌کند تا تعداد بررسی‌ها کمتر شود.

فرض می‌کنم دکمه ثبت‌نام سایت در نسخه فعلی خراب است، اما در کامیت فرضی `a1b2c3d` درست کار می‌کرده. اول جست‌وجو را شروع می‌کنم:

```bash
git bisect start
git bisect bad HEAD
git bisect good a1b2c3d
```

بعد Git یکی از کامیت‌های بین نسخه سالم و خراب را انتخاب می‌کند. پروژه را در آن نسخه امتحان می‌کنم:

- اگر مشکل وجود نداشت، می‌زنم `git bisect good`.
- اگر مشکل وجود داشت، می‌زنم `git bisect bad`.

این کار را تکرار می‌کنم تا Git اولین کامیتی را که باعث خطا شده مشخص کند. در آخر هم از حالت جست‌وجو خارج می‌شوم:

```bash
git bisect reset
```

به نظرم این روش مخصوصاً وقتی تعداد کامیت‌ها زیاد باشد خیلی کاربردی است، چون لازم نیست همه نسخه‌ها را یکی‌یکی بررسی کنم.

## سؤال ۴: بررسی تغییرات قبل از کامیت

در صورت سؤال، فایل `README.md` از قبل تحت پیگیری Git بوده است. یک سری تغییر را وارد `staging` کرده‌ام و بعد دوباره فایل را تغییر داده‌ام، اما تغییرات جدید را هنوز به `staging` نفرستاده‌ام.

**۱. بررسی وضعیت و تغییرات**

```bash
git status
git diff -- README.md
git diff --cached -- README.md
```

- `git status` وضعیت فایل‌ها و تغییرات `staged` و `unstaged` را نشان می‌دهد.
- `git diff -- README.md` تغییرات فایل محلی نسبت به نسخه داخل `staging` را نشان می‌دهد؛ یعنی تغییرات جدیدی که هنوز آماده کامیت نشده‌اند.
- `git diff --cached -- README.md` تغییرات داخل `staging` نسبت به آخرین کامیت را نشان می‌دهد؛ یعنی همان قسمت‌هایی که آماده ثبت هستند.

اگر بخواهم همه تغییرات فایل نسبت به آخرین کامیت را یک‌جا ببینم، از این دستور استفاده می‌کنم:

```bash
git diff HEAD -- README.md
```

**۲. اگر همین الان یک کامیت معمولی ثبت کنم**

```bash
git commit -m "Update README"
```

فقط تغییراتی که قبلاً وارد `staging` کرده‌ام ثبت می‌شوند. ویرایش‌هایی که بعداً انجام داده‌ام و هنوز `stage` نشده‌اند، در `working tree` باقی می‌مانند. دلیلش هم این است که `git commit` معمولی، بدون گزینه `-a`، خودش تغییرات جدید فایل را به `staging` اضافه نمی‌کند.

**۳. جلوگیری از ثبت فایل‌های موقت**

در فایل `.gitignore` که در ریشه مخزن قرار دارد، این خط را می‌نویسم:

```gitignore
tmp/
```

با این کار، Git فایل‌های `untracked` داخل پوشه `tmp/` را نادیده می‌گیرد. اما اگر یک فایل قبلاً `tracked` شده باشد، اضافه کردن آن به `.gitignore` کافی نیست. باید آن را از فهرست فایل‌های تحت پیگیری خارج کنم، بدون اینکه از کامپیوترم پاک شود:

```bash
git rm --cached -- path/to/tracked-file
```

اگر چند فایل tracked داخل پوشه `tmp/` وجود داشته باشد، می‌توانم از دستور زیر استفاده کنم:

```bash
git rm -r --cached -- tmp/
```

بعد هم باید این تغییر را کامیت کنم. فایل‌های اصلی روی سیستمم باقی می‌مانند.

## سؤال ۵: رفع merge conflict در کار گروهی

**۱. علت به وجود آمدن conflict**

من در شاخه `feature-description` و هم‌تیمی‌ام در `main` یک خط مشترک از `README.md` را به دو شکل متفاوت عوض کرده‌ایم. موقع ادغام، Git نمی‌تواند خودش تشخیص بدهد کدام متن باید باقی بماند؛ برای همین `conflict` ایجاد می‌شود.

البته هر تغییری که دو نفر در یک فایل بدهند لزوماً باعث conflict نمی‌شود. اگر قسمت‌های جداگانه‌ای از فایل را تغییر داده باشند، Git معمولاً خودش آن‌ها را ادغام می‌کند.

**۲. پیدا کردن فایل و قسمت‌های دارای conflict**

```bash
git switch main
git merge feature-description
git status
git diff --name-only --diff-filter=U
```

`git status` فایل‌های دارای مشکل را نشان می‌دهد و دستور آخر اسم فایل‌هایی را می‌دهد که تداخلشان هنوز حل نشده است. داخل فایل ممکن است چیزی شبیه این ببینم:

```text
<<<<<<< HEAD
متن شاخه main
=======
متن شاخه feature-description
>>>>>>> feature-description
```

علامت `<<<<<<<` شروع متن یک طرف است (اینجا `HEAD` یعنی `main`). علامت `=======` دو نسخه را جدا می‌کند و `>>>>>>>` انتهای متن طرف دوم را نشان می‌دهد. این علامت‌ها فقط برای مشخص شدن محل اختلاف هستند و نباید در متن نهایی باقی بمانند.

**۳. حل کردن conflict و کامل کردن merge**

چون در سؤال گفته شده اطلاعات هر دو نفر باید حفظ شود، فایل را باز می‌کنم و یک متن جدید می‌نویسم که هر دو تغییر در آن باشد. مثلاً:

> برای این پروژه هم راهنمای نصب نوشته شده و هم امکانات جدید آن توضیح داده شده است.

بعد علامت‌های conflict را از فایل حذف می‌کنم و متن را دوباره می‌خوانم تا مطمئن شوم چیزی جا نمانده است. سپس این دستورها را اجرا می‌کنم:

```bash
git add README.md
git diff --cached --check
git status
git merge --continue
git status
```

`git add` به Git اعلام می‌کند که تداخل این فایل را حل کرده‌ام. دستور `git diff --cached --check` هم می‌تواند بعضی خطاها، از جمله علامت‌های conflict باقی‌مانده در تغییرات آماده ثبت، را پیدا کند. با این حال خود فایل را هم بررسی می‌کنم. در نهایت `git merge --continue` ادغام را کامل می‌کند و با `git status` وضعیت نهایی را می‌بینم.

**۴. اگر بخواهم ادغام را لغو کنم**

```bash
git merge --abort
```

این دستور merge در حال انجام را لغو می‌کند. چون طبق صورت سؤال قبل از شروع ادغام تغییر ثبت‌نشده‌ای نداشته‌ایم، وضعیت به قبل از merge برمی‌گردد.

## سؤال ۶: انتخاب روش مناسب برای برگرداندن تغییرات

**حالت اول: تغییرات notes.txt هنوز وارد staging نشده‌اند و دیگر آن‌ها را نمی‌خواهم.**

```bash
git restore --worktree -- notes.txt
```

این دستور تغییرات فایل را در `working tree` کنار می‌گذارد و نسخه داخل `staging` را برمی‌گرداند. در این سؤال، نسخه staging همان نسخه آخرین کامیت است. بقیه فایل‌ها، staging و تاریخچه کامیت‌ها تغییر نمی‌کنند. باید حواسم باشد که با این دستور ممکن است ویرایش‌های کنارگذاشته‌شده را از دست بدهم.

**حالت دوم: فایل را اشتباهی وارد staging کرده‌ام، ولی می‌خواهم ویرایش‌هایم بمانند.**

```bash
git restore --staged -- notes.txt
```

این دستور تغییرات فایل را از `staging` خارج می‌کند، ولی متن ویرایش‌شده در `working tree` باقی می‌ماند. تاریخچه کامیت‌ها هم عوض نمی‌شود.

**حالت سوم: یک کامیت اشتباه را روی main پوش کرده‌ام و بقیه هم آن را دریافت کرده‌اند.**

```bash
git switch main
git revert <commit-hash>
git push origin main
```

در این دستور، به‌جای `<commit-hash>` شناسه کامیت اشتباه را می‌گذارم. `git revert` یک کامیت جدید می‌سازد که اثر کامیت اشتباه را برعکس می‌کند، بدون اینکه خود آن کامیت را از تاریخچه پاک کند. بعد با `git push` نتیجه را برای بقیه می‌فرستم. با فرض سؤال که conflict نداریم، بعد از تکمیل کار معمولاً `working tree` دوباره تمیز می‌شود.

اینجا `reset` همراه با `force push` انتخاب خوبی نیست، چون تاریخچه شاخه مشترک را بازنویسی می‌کند و ممکن است کار هم‌تیمی‌هایی را که آن کامیت را دریافت کرده‌اند به مشکل بیندازد. برای همین `revert` راه مناسب‌تری است.
